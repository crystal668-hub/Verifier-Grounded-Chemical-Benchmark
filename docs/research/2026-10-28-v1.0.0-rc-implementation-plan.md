- Work on `chore/v1.0.0-rc`; test every coherent change before committing it.

## 1. Evaluation and configuration fixes

1. Make the CLI emit its report and return a nonzero status for evaluator or
   infrastructure failures. Normal evaluated zero scores remain successful runs.
2. Classify overflowing numeric submissions as invalid values instead of
   aborting a batch; retain all other rows.
3. Validate scoring-config identity and version against task-pack metadata.
4. Reject duplicate keys in task, scoring, and verifier YAML, with resource
   and line diagnostics; preserve supported YAML anchors.
5. Add focused regressions for runtime errors, large integers, bad identities,
   mismatched versions, duplicate keys, and ordinary zero-score behavior.

Acceptance: focused evaluation/loader/CLI tests and Ruff pass; the 100 task packs
still load; normal gold scores and aggregation remain unchanged.

## 2. RC versioning and protected release construction

1. Synchronize project, lockfile, registered track, task-pack and scoring-config
   versions. Update current-version tests without rewriting historical assertions.
2. Accept an explicit release tag independently of the normalized Python version.
3. Reject dirty source, noncanonical versions, conflicting tags, occupied output
   paths, and mismatched task/scoring/registry versions before building.
4. Build in a temporary staging directory, verify wheel/sdist contents and
   metadata, and publish new local artifacts without overwriting existing files.
5. Record source commit/tree, resource hashes, task inventory, artifact hashes,
   and the explicit version/tag mapping.
6. Add regressions proving refusal happens before destructive work or builds.

Acceptance: preflight and packaging tests pass; repeated builds from identical
source have identical hashes; historical releases remain untouched.

## 4. Source acceptance, artifact acceptance and publication

1. Run all Python-package tests, lint, lockfile consistency and clean-core checks.
2. Verify scientific inputs and scoring boundaries; test 70 property-task gold
   round trips, all 10 RDKit samples, and the nine available xTB/CREST samples.
3. Keep remaining xTB tasks, repeat-run stability and independent gold validation
   explicitly unverified unless suitable evidence is actually executed.
4. Commit accepted source. Build and tag only the accepted commit; release
   documentation/attestation generated afterward must identify that source.
5. Install the exact candidate wheel into an isolated environment, run outside
   the checkout, check CLI coverage and errors, compare wheel/sdist payloads,
   and verify exclusions and historical artifact hashes.
6. Complete the RC notes and machine-readable acceptance record. Publish only
   to the user-confirmed destination after the applicable gates pass.
